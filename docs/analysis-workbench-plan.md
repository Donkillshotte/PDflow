# PDflow Analysis Workbench — Execution Plan

Status: implementation in progress — core vertical slice operational
Primary certified profile: ASAP7
Scope: FlowLab, Product, Package, System PDN, Lab, native tools, reports, and UI orchestration

## Implementation status and verification

The first implementation slice is now present in the repository.  The local
agent owns the versioned check policy, native-tool registry, resource-aware job
queue, artifact resolution, candidate isolation, report normalization, and
event-driven invalidation.  The browser facade and the desktop shell consume
the same agent contracts; they do not launch shell commands or maintain a
second copy of stage policy.

Implemented vertical-slice capabilities include:

- checkpoint-aware check eligibility for FlowLab, Package, and Lab scopes;
- separate execution, evidence, requirement, and signoff status dimensions;
- explicit read-only analysis-bundle preflight followed by a confirmed queue
  boundary;
- single-slot native execution with cgroup/systemd isolation and a default
  600-second timeout;
- atomic candidate dependency closure for native checkpoint analysis, with all
  candidate inputs and outputs recorded in provenance;
- bounded log/event handling, stale propagation, and protected finish
  artifacts;
- shared Workbench UI controls for timing, power integrity, grid, IR, EM,
  Package/System PDN, and Lab evidence;
- native RTL-to-GDS verification on the real GCD RTL, including OpenROAD,
  OpenSTA, KLayout, Yosys, Icarus, ngspice, and the declared proxy adapters.

The current strict native GCD run is an honest execution result, not a claim
of timing closure: OpenSTA generated valid evidence with `WNS=-0.16 ns`,
`TNS=-5.61`, and 44 setup violations at the selected 0.46 ns requirement.
Its report is `execution_status=COMPLETED`, `evidence_status=PASS`,
`requirement_status=FAIL`, `signoff_status=FAIL`, and
`product_signoff=false`.  The end-to-end software gate may continue past this
known design requirement failure only when
`PD_FLOW_E2E_ALLOW_TIMING_FAIL=1` is explicitly in force; a Product timing
gate must use `PD_FLOW_E2E_ALLOW_TIMING_FAIL=0` and require a passing
requirement result.

Known capability boundaries remain visible by contract: Signal EM is `GAP`
until a qualified native engine and rule source are integrated; dynamic IR,
VYGES EM/IR, and Package/System PDN may be `PROXY` when their evidence is
useful but not sufficient for Product signoff.  Nangate45 GCD remains a
legacy/course profile while ASAP7 is the primary workbench target.  These
states are intentionally not promoted to Product badges.

## 1. Objective

Turn the currently scattered timing, PDN, IR, EM, power, DRC, LVS, and package results into one coherent analysis workflow.

The application must answer five questions without requiring the user to inspect raw JSON or know which script to run:

1. Which analyses are meaningful at the selected physical checkpoint?
2. Which inputs are present, missing, stale, estimated, or incompatible?
3. Which native tool and exact configuration produced each result?
4. Does the result describe execution success, valid evidence, or an actual design requirement pass?
5. What should the user run next, and what downstream evidence will become stale?

The plan deliberately separates analysis availability from stage names. A check is eligible because the selected checkpoint satisfies its declared prerequisites, not merely because the UI is displaying a particular tab.

## 2. Problems to correct

### 2.1 Results are fragmented

- Grid connectivity is launched from the FlowLab PDN phase, but the detailed result is primarily a log.
- Stage WNS and timing reports exist in ORFS reports, while full STA lives in Finish signoff.
- Static chip IR is generated by the power signoff path.
- Advanced dynamic IR is a separate explicit action and is not part of `signoff_all`.
- Power-grid EM details are nested inside the dynamic IR report and are easy to miss.
- Signal EM has no qualified engine or report and must currently be represented as `GAP`.
- System PDN belongs to Package and is not a chip PDN result.
- Tools, Results, Inspect, Finish, and Package expose overlapping fragments without one checkpoint-aware model.

### 2.2 Completion is confused with signoff

The current evaluation path can treat a finite measurement as successful evidence even when the design requirement is violated. A negative WNS and non-zero setup violation count can therefore coexist with `ok=true`.

This must be replaced by four independent dimensions:

- `execution_status`: did the process run successfully?
- `evidence_status`: are the inputs, provenance, parser, and units valid?
- `requirement_status`: does the measured value satisfy the declared requirement?
- `signoff_status`: are all mandatory checks current, comparable, and passing?

`COMPLETED` must never imply `PASS`.

### 2.3 Check availability is not explicit

Today the UI does not consistently explain whether an analysis is:

- impossible at the current checkpoint;
- technically runnable but exploratory;
- runnable with incomplete inputs;
- suitable as Product evidence;
- blocked by a missing native tool or rule deck.

Every action needs an eligibility result and a human-readable reason.

## 3. Architectural decisions

### 3.1 ASAP7-first, PDK-aware contracts

- ASAP7 becomes the primary certified profile for the integrated workbench.
- Design, PDK, corner, mode, voltage domain, and checkpoint are mandatory context fields.
- Existing Nangate45 course artifacts remain supported as explicitly labelled educational or legacy profiles.
- No result from one PDK, corner, stage, mesh, activity source, or run is silently compared with another.

### 3.2 Checkpoints are immutable inputs

Every physical stage produces a checkpoint reference:

```text
checkpoint_id
run_id
design_id
pdk_id
stage
artifact_id
artifact_hash
created_at
authority
revision
available_capabilities
```

Analyses read a checkpoint. A geometry-changing operation creates or advances a candidate checkpoint and invalidates dependent analyses. The finish remains immutable.

### 3.3 One eligibility engine

Introduce a versioned `CheckDescriptor` registry shared by Python and TypeScript:

```text
check_id
scope
display_name
eligible_stages
required_artifact_kinds
required_checkpoint_capabilities
required_inputs
required_tool_capabilities
engine
default_trigger
cost_class
resource_profile
timeout_seconds
knob_schema
output_schema
requirement_policy
invalidate_on
comparison_contract
```

The local agent evaluates the descriptor and returns:

```text
eligible
execution_class
expected_evidence_class
missing_inputs[]
stale_inputs[]
incompatible_inputs[]
estimated_inputs[]
blocking_reasons[]
warnings[]
estimated_duration
resource_limit
downstream_invalidations[]
```

The UI renders this response. It does not duplicate stage policy in React.

### 3.4 Explicit execution bundles

Navigating, opening an inspector, or selecting a tab must remain read-only.

Each stage exposes two explicit actions:

- `Run stage`: execute only the selected stage and its mandatory lightweight validators.
- `Run stage + recommended checks`: show a preflight list, then execute the stage and the recommended eligible checks after user confirmation.

Heavy STA, IR, EM, DRC, LVS, SPICE, build, and desktop jobs remain in the isolated single-job queue with a 600-second timeout unless an adapter explicitly declares another reviewed limit.

## 4. Canonical stage and check policy

The labels below define the default ASAP7 policy. The runtime eligibility engine still verifies actual inputs.

### 4.1 RTL

Available:

- RTL lint and compile.
- RTL simulation and waveform generation.
- Activity capture from simulation.
- Clock and constraint syntax validation.

Not meaningful:

- PDN generation or grid connectivity.
- Static or dynamic IR.
- Power-grid or signal EM.
- Physical DRC and LVS.

Timing at RTL is constraint intent only. It is not STA evidence.

### 4.2 Synthesis

Available:

- Synthesis and technology mapping.
- Netlist checks and equivalence where configured.
- Area, cell count, hierarchy, and unmapped-cell reports.
- Pre-layout STA with ideal or estimated interconnect.
- Vectorless or activity-backed power estimate.

Classification:

- Pre-layout STA is `PROXY` for physical closure.
- Power is `PROXY` unless activity coverage and the model are explicitly qualified.
- No PDN, IR, or EM action is enabled because no physical power mesh exists.

### 4.3 Floorplan and PDN construction

Available:

- Floorplan creation.
- PDN generation on a candidate.
- PDN geometry sanity checks.
- VDD/VSS grid connectivity check.
- Early congestion and utilization estimates.
- Early timing estimate when an accepted wire model exists.

Default behavior:

- PDN generation is a geometry-changing operation and runs only on a candidate.
- Gridcheck runs automatically as a lightweight postcondition of a user-started floorplan/PDN generation job.
- Gridcheck can also be re-run manually without changing geometry.

IR policy:

- No Product static IR is offered because placed instance currents are unavailable.
- A deliberately selected synthetic uniform-load experiment may run in Lab and is always `PROXY`.
- Dynamic IR and EM remain unavailable in FlowLab at this stage.

### 4.4 Placement

Available:

- Placement legality and density checks.
- Grid connectivity against the placement checkpoint.
- Placement-stage STA with estimated RC.
- Activity and per-instance power join.
- Early static IR when a placed current map and voltage sources exist.
- Optional exploratory dynamic IR when a declared activity/current waveform model exists.

Classification:

- Timing is pre-CTS and must be labelled estimated-clock timing.
- Static IR is `PROXY` or `PARTIAL`, never final Product signoff.
- Dynamic IR is opt-in and `PROXY` because clocks and routed interconnect are incomplete.
- Power-grid EM may be computed for exploration, but cannot pass without qualified geometry and limits.

### 4.5 CTS

Available:

- Clock tree integrity, insertion delay, skew, and buffer reports.
- Propagated-clock STA.
- Grid connectivity against the CTS checkpoint.
- Clock-aware static IR.
- Activity-backed exploratory dynamic IR.
- Clock-network hotspot analysis.

Classification:

- Timing is more representative but pre-route.
- Static and dynamic IR remain `PARTIAL` unless all required extraction and current inputs are qualified.
- Power-grid EM remains analytical and cannot become a foundry pass without an EM rule source.

### 4.6 Route

Available:

- Routed geometry and route DRC.
- Antenna checks.
- Grid connectivity against the routed checkpoint.
- Routed or extracted-RC STA.
- Static IR with routed power geometry.
- Dynamic IR with activity/current waveforms.
- Power-grid EM hotspot analysis.
- Signal EM only if a dedicated engine, signal current model, extracted route geometry, and layer/via limits are available.

Classification:

- Route STA and IR can be candidate-quality evidence but remain pre-finish.
- Power-grid EM is `PARTIAL` when widths are inferred or foundry limits are absent.
- Signal EM is currently `GAP`; route DRC and antenna checks are not substitutes.

### 4.7 Finish

Available:

- Final checkpoint validation.
- Final extracted STA across configured modes and corners.
- Final static IR.
- Final dynamic IR.
- Power-grid EM.
- Signal EM when the missing engine and qualified rule deck have been integrated.
- GDS DRC.
- LVS.
- Product signoff aggregation.

Product eligibility requirements:

- Every mandatory input hash matches the selected finish checkpoint.
- Reports are current and belong to the same run and compatible configuration.
- Required corners and modes are complete.
- Requirement thresholds come from a versioned design/PDK policy.
- No mandatory check is `GAP`, `PARTIAL`, `PROXY`, `NOT_RUN`, `STALE`, or `FAIL`.

### 4.8 Package and System PDN

System PDN is not a FlowLab chip stage. It becomes eligible when Package has:

- a chip/package interface definition;
- bump or pad mapping;
- voltage domains and return paths;
- chip current/load profile;
- package/board/VRM model;
- ngspice or Xyce available.

Typical policy:

- Route checkpoint plus complete package inputs: exploratory `PROXY` or `PARTIAL` run.
- Finish checkpoint plus complete package inputs: package evidence.
- Missing SPICE engine or incomplete package model: `GAP`.
- Package evidence never becomes Product chip signoff automatically.

## 5. Detailed analysis contracts

### 5.1 PDN generation versus PDN validation

The UI must stop using “PDN” as one ambiguous action.

Expose distinct operations:

- `Generate PDN`: mutates candidate geometry; normally Floorplan only.
- `Check connectivity`: read-only; Floorplan, Place, CTS, Route, and Finish.
- `Analyze static IR`: read-only analysis; Place onward when current and source inputs exist.
- `Analyze dynamic IR`: read-only analysis; Place onward with stage-dependent evidence class.
- `Analyze power-grid EM`: read-only analysis; Route and Finish by default.
- `Analyze signal EM`: Route and Finish only, currently disabled as `GAP`.

If PDN parameters are edited after Placement, PDflow must create a new candidate lineage and mark Place, CTS, Route, Finish, STA, DRC, LVS, IR, and EM evidence stale. It must not patch the existing finish.

### 5.2 Grid connectivity

Normalize every execution into structured JSON rather than relying on a log stamp.

Required output:

```text
nets_checked[]
connected_components_per_net
unconnected_shapes
missing_terminals
shorts_or_cross_net_anomalies
checkpoint_id
artifact_hash
tool_version
raw_log_artifact_id
```

The current VDD/VSS connected message remains visible, but the UI also shows per-net results and the exact checkpoint.

### 5.3 STA and slack

Provide a stage-aware timing workspace with:

- WNS and TNS for setup and hold.
- Violation counts.
- Worst slack and endpoint.
- Path table with startpoint, endpoint, group, delay, slack, and corner.
- Clock period and minimum period.
- Constraint coverage and unconstrained endpoints.
- Corner/mode completeness.
- RC source and extraction quality.
- Nominal versus IR-aware timing where comparable.

Stage labels must be explicit: ideal interconnect, estimated RC, propagated clock, routed RC, or final SPEF.

Requirement evaluation defaults:

- setup WNS must meet the declared target, normally at least zero;
- setup TNS must meet the declared target, normally zero;
- mandatory setup violations must be zero;
- hold requirements are evaluated separately;
- unconstrained mandatory endpoints are blocking;
- merely parsing finite values is evidence validity, not requirement success.

### 5.4 Static IR

Required views:

- die heatmap when spatial data exists;
- worst droop, percentage, location, net, and domain;
- source and sink summary;
- top hotspot table;
- per-layer and per-region statistics;
- current-map coverage;
- model assumptions and solver convergence;
- checkpoint comparison when compatible.

The result can be `PASS` only if a versioned threshold and qualified input model exist. Otherwise it is `PARTIAL`, `PROXY`, or `GAP` with the exact reason.

### 5.5 Dynamic IR

Required views:

- time waveform and worst-time marker;
- spatial heatmap at selected time;
- static baseline versus dynamic droop;
- VDD droop and VSS bounce;
- activity coverage and source;
- waveform construction model;
- solver, convergence, time step, duration, and reduction method;
- hotspots and affected timing paths;
- explicit limitations such as NLDM-only power or synthetic triangle currents.

Dynamic IR must not be hidden under a generic advanced disclosure. It becomes a first-class Power Integrity view.

### 5.6 Power-grid EM

Required views:

- current and current-density maps by layer and via class;
- top branches and vias;
- geometry source: exact, extracted, inferred, or missing;
- temperature and lifetime assumptions;
- current mode: average, RMS, or peak;
- foundry limit source and rule version;
- relative TTF only when absolute foundry calibration is unavailable.

No foundry limit means no EM pass badge. Relative lifetime and hotspot ranking remain useful analysis but must be labelled `PARTIAL` or `PROXY`.

### 5.7 Signal EM

Signal EM remains an explicit integration gap until all of the following exist:

- routed signal and clock geometry;
- average/RMS/peak current estimation per net;
- layer and via current limits;
- temperature model;
- qualified engine and parser;
- reproducible validation fixture.

The GUI must show the missing capability and remediation path. It must never substitute antenna, route DRC, or power-grid EM.

### 5.8 DRC and LVS

- Floorplan: boundary, macro, keepout, and PDN geometry sanity.
- Placement: legality and placement-specific checks.
- Route: route DRC and antenna.
- Finish: fresh GDS DRC using the selected deck.
- LVS: Finish only, requiring GDS, netlist/CDL, extraction, and matched top-cell identity.

Non-zero mandatory DRC violations are `FAIL`, not valid success. LVS is `PASS` only when the declared equivalence policy is satisfied.

## 6. Unified GUI information architecture

### 6.1 Analysis rail

Add a checkpoint-aware analysis rail next to the stage navigation. It shows, for the selected checkpoint:

- eligible checks;
- completed/current checks;
- stale checks;
- missing prerequisites;
- queued/running jobs;
- recommended next action.

Selecting an item changes the central view but does not launch a job.

### 6.2 Central workbench views

Use consistent primary views across FlowLab, Product, and Package:

- `Design`: layout, RTL, waveform, or geometry.
- `Timing`: STA summary, paths, clocks, and constraints.
- `Power Integrity`: gridcheck, static IR, dynamic IR, and waveforms.
- `EM / Thermal`: power-grid EM, signal EM, thermal context, and limitations.
- `Checks`: stage-local DRC, LVS, connectivity, and requirement matrix.
- `Reports`: normalized reports, provenance, raw logs, and downloads.

Views appear only when relevant, but missing mandatory analyses remain visible as explicit states rather than disappearing.

### 6.3 Inspector

The right inspector contains contextual information, not duplicate dashboards:

- artifact identity, hash, authority, and revision;
- check prerequisites and eligibility explanation;
- configuration knobs and presets;
- provenance and tool versions;
- selected hotspot, path, net, or violation details;
- invalidation impact before a run.

### 6.4 Dock and timeline

The bottom dock provides:

- preflight plan;
- queue position and resource limit;
- process status and termination cause;
- bounded live log;
- stage/check events;
- links to complete logs and reports.

No separate console is duplicated inside each analysis page.

### 6.5 Report discovery

Results currently exposed through Tools, Results, Inspect, and Finish are indexed by one evidence query and rendered in the selected stage context.

Tools remains responsible for:

- registry and version diagnostics;
- adapter configuration;
- raw operation history;
- recovery and support workflows.

It is not the primary place to understand design results.

## 7. Knob model

Every knob is typed, versioned, validated, and associated with an analysis or geometry operation.

### 7.1 Geometry-changing knobs

Examples:

- die/core area and utilization;
- macro/channel/halo settings;
- PDN layers, pitch, width, spacing, offset, ring, stripe, and via policy;
- placement density and padding;
- CTS targets and buffer policy;
- routing layer bounds and adjustment.

Rules:

- available only on candidates;
- show downstream invalidation before execution;
- save as a candidate recipe;
- never mutate finish artifacts.

### 7.2 Analysis-only knobs

Timing:

- corner and mode;
- max/min analysis;
- SDC profile;
- propagated versus ideal clock where valid;
- path groups, endpoint filters, and path count;
- RC source.

Power integrity:

- voltage domain and net;
- voltage-source model;
- activity source;
- vectorless assumptions;
- current waveform model;
- peak factor;
- simulation duration and time step;
- decap and package RLC assumptions;
- solver and convergence tolerance.

EM and thermal:

- average/RMS/peak current mode;
- temperature source;
- lifetime target;
- rule deck;
- layer/via filter;
- electrothermal iteration policy.

Analysis-only knobs create a new analysis configuration and report. They do not alter geometry.

### 7.3 Presets

Provide reviewed presets such as:

- `Fast stage health`;
- `Recommended checkpoint analysis`;
- `Final timing`;
- `Final power integrity`;
- `Package system PDN`;
- `Exploratory lab`.

The preflight always expands a preset into concrete jobs, tools, inputs, resource limits, and expected evidence class before launch.

### 8.1 New records

Introduce:

- `CheckpointRef`;
- `CheckDescriptor`;
- `EligibilityResult`;
- `AnalysisConfig`;
- `AnalysisRun`;
- `EvidenceRecord`;
- `RequirementEvaluation`;
- `AnalysisBundle`.

Every evidence record includes:

```text

checkpoint_id
analysis_run_id

```

### 8.2 Additive endpoints

```text
GET  /api/checks?checkpoint_id=...
GET  /api/checks/:checkId/eligibility?checkpoint_id=...
POST /api/analysis-runs
GET  /api/analysis-runs/:analysisRunId
POST /api/analysis-bundles/preview
POST /api/analysis-bundles
GET  /api/evidence?checkpoint_id=...&check_id=...
GET  /api/evidence/:reportId
POST /api/evidence/compare
```

The existing routes remain facades during migration. Arbitrary filesystem paths remain forbidden.

The implemented Workbench facade currently exposes these additive routes:

```text
GET  /api/registry
GET  /api/context
GET  /api/checks?stage=finish&variant=flowlab
GET  /api/evidence?stage=finish&variant=flowlab
POST /api/analysis-bundles/preview
POST /api/analysis-bundles
POST /api/analysis-runs
GET  /api/analysis-runs
GET  /api/analysis-runs/:analysisRunId
GET  /api/artifacts/:artifactId
GET  /api/reports/:reportId
POST /api/compare
```

`POST /api/analysis-bundles/preview` is a typed, read-only preflight.  It
returns the expanded checks, eligibility reasons, native actions, estimated
duration, resource queue, required evidence class, and downstream
invalidations without creating a process.  Only a request carrying explicit
confirmation is forwarded to `POST /api/analysis-bundles`; that request creates
or reuses one single-use `AnalysisRun` and submits runnable jobs through the
local agent's single heavy-job queue.  Repeating an active or completed
analysis run is idempotent; retrying a failed run requires a new analysis-run
identifier so the original evidence remains auditable.

### 8.3 Invalidation

An evidence record becomes stale when any declared dependency changes:

- checkpoint artifact hash;
- design, PDK, corner, or mode;
- SDC, Liberty, SPEF, activity, package, or rule-deck hash;
- analysis configuration;
- relevant tool/parser version;
- upstream report used as an input.

Aggregates such as `signoff_all` subscribe to child evidence revisions. A newer child report immediately invalidates the aggregate until it is recomputed.

## 9. Orchestration and default triggers

### 9.1 Automatic lightweight postconditions

Allowed only as part of a user-started stage job:

- artifact existence, schema, and hash validation;
- stage log parse;
- placement legality where already produced by the stage;
- route summary parse;
- grid connectivity after PDN-bearing checkpoints when runtime cost remains lightweight;
- report freshness calculation.

### 9.2 Explicit recommended checks

Run only after preflight confirmation:

- stage-local STA beyond reports already produced by the stage;
- static IR;
- dynamic IR;
- power-grid EM;

### 9.3 Explicit final bundles

`Final timing`, `Final power integrity`, `GDS verification`, and `Product signoff` are separate visible bundles.

`Product signoff` may depend on the other bundles, but it must not hide which jobs will run. Dynamic IR and EM are not silently excluded or included; the active requirement policy declares whether they are mandatory.

### 9.4 Resource behavior

- One heavy job at a time.
- Native tools only for certified execution.
- cgroup v2 / user-systemd isolation.
- 600-second default timeout.
- descendant termination on cancel or timeout.
- full logs on disk, bounded frontend log buffer.
- OOM, timeout, crash, cancellation, dependency gap, and requirement failure reported separately.

## 10. Implementation sequence

### Phase 0 — Inventory and policy freeze

- Inventory every current script, action, report, parser, checkpoint, and UI entry point.
- Record current ASAP7 and legacy profile coverage.
- Define canonical units and identifiers.
- Approve the stage/check policy and Product mandatory-check policy.
- Add deterministic fixtures for missing, stale, partial, proxy, and failing evidence.

Gate: every current result has an owner, stage, scope, schema status, and migration destination.

### Phase 1 — Correct status semantics first

- Split execution, evidence, requirement, and signoff status.
- Correct STA evaluation so negative WNS and open mandatory violations fail.
- Correct DRC evaluation so non-zero mandatory violations fail.
- Require an explicit IR threshold before IR can pass.
- Require qualified EM limits before EM can pass.
- Invalidate aggregates when child evidence changes.
- Add regression tests for every semantic correction.

Gate: no `ok=true` can be produced solely because a metric is finite or non-negative.

### Phase 2 — Normalized evidence and checkpoint model

- Add `CheckpointRef` and evidence schemas.
- Normalize gridcheck, stage timing, final STA, static IR, dynamic IR, power-grid EM, DRC, LVS, and System PDN.
- Import existing report paths as legacy evidence with explicit comparability limits.
- Implement hash- and revision-based invalidation.

Gate: the UI can query all evidence through one API without parsing raw tool logs.

### Phase 3 — Eligibility engine and stage-specific adapters

- Implement the descriptor registry and backend eligibility evaluation.
- Generalize gridcheck from a hard-coded floorplan ODB to selected PDN-bearing checkpoints.
- Add stage-aware STA adapters.
- Add stage-aware static/dynamic IR adapters where the native engine supports the checkpoint.
- Return precise disabled reasons for unsupported combinations.

Gate: every stage/check combination is deterministically available, exploratory, partial, gap, or unavailable.

### Phase 4 — Bundle planner and safe execution

- Implement bundle preview.
- Show prerequisites, jobs, costs, resource limits, outputs, and invalidations.
- Execute through the existing isolated local-agent queue.
- Add cancellation, crash recovery, and stale propagation.

Gate: no navigation or panel opening launches a job; all heavy work has an explicit preflight.

### Phase 5 — GUI workbench foundation

- Add the analysis rail and shared central views.
- Replace scattered Results/Inspect fragments with checkpoint-aware evidence panels.
- Add the shared inspector and dock integration.
- Preserve deep links and current artifact context.
- Implement empty, missing, stale, proxy, partial, gap, fail, and pass states.

Gate: the user can discover all available analyses and understand why each action is enabled or disabled.

### Phase 6 — Timing experience

- Stage-aware WNS/TNS cards.
- Setup/hold separation.
- Path table and path detail.
- Clock/skew and constraint coverage.
- Corner/mode selector and completeness matrix.
- Nominal versus IR-aware timing comparison.

Gate: Synth through Finish timing is visible with correct evidence qualification and no cross-stage ambiguity.

### Phase 7 — PDN, IR, EM, and thermal experience

- Structured grid connectivity view.
- Static and dynamic IR heatmaps, waveforms, hotspots, and provenance.
- Power-grid EM maps and top-offender views.
- Clear Signal EM `GAP` view until its backend is integrated.
- Thermal/electrothermal limitations and correlations.

Gate: no important IR/EM metric remains hidden in nested disclosures or raw JSON.

### Phase 8 — Package and System PDN integration

- Reuse the same evidence and eligibility contracts in Package.
- Link chip load/interface evidence to the package run.
- Expose RLC knobs and SPICE provenance.
- Keep chip and system PDN scopes visually and semantically distinct.

Gate: System PDN is linear, inspectable, and cannot influence Product status implicitly.

### Phase 9 — Signal EM capability

- Select and integrate a qualified native engine.
- Add extracted signal-current and route-geometry joins.
- Add ASAP7 layer/via limits with source/version provenance.
- Validate against reproducible fixtures.

Gate: Signal EM moves from `GAP` only after numerical and rules validation.

### Phase 10 — Certification and documentation

- Run complete native ASAP7 RTL-to-GDS flows on representative real RTL designs.
- Exercise every eligible checkpoint analysis.
- Verify Product, Package, and Lab isolation.
- Complete UI viewport, accessibility, performance, and long-session testing.
- Publish English operator, architecture, adapter, and interpretation guides.

Gate: signed evidence matrix and unchanged finish hashes.

## 11. Verification plan

### 11.1 Policy and semantic tests

- Every check/stage combination has an expected eligibility result.
- Disabled actions include deterministic reasons.
- Negative WNS produces requirement `FAIL`.
- Open setup violations produce `FAIL`.
- Non-zero mandatory DRC produces `FAIL`.
- Missing IR threshold prevents `PASS`.
- Missing EM limits produces `GAP` or `PARTIAL`.
- A newer child report invalidates `signoff_all`.
- Incompatible mesh, corner, activity, checkpoint, or run prevents delta calculation.

### 11.2 Backend and adapter tests

- Schema and unit validation.
- Parser fixtures for every native tool version.
- Missing executable and malformed report behavior.
- Cancellation of descendant processes.
- OOM, timeout, crash, and recovery.
- Lock release and candidate isolation.
- Event coalescing and bounded logs.

### 11.3 UI tests

- Navigation and inspectors never launch jobs.
- All data states render without misleading color or badge.
- Long paths, net names, corners, logs, and violation lists remain usable.
- Knob validation and preset expansion are visible before execution.
- Rapid checkpoint changes cannot display late results from the previous context.
- Charts preserve units, zero, negative values, and missing values correctly.
- Keyboard, zoom, narrow viewport, and ultrawide layouts remain functional.

### 11.4 Native end-to-end acceptance

For each selected real ASAP7 RTL design:

1. Create an isolated candidate.
2. Run RTL simulation and activity capture.
3. Run synthesis and pre-layout STA.

## 12. Definition of Done

The work is complete only when:

- The user can see every relevant timing, PDN, IR, EM, DRC, LVS, and System PDN result from the selected checkpoint.
- Every analysis action is enabled only when its real prerequisites are satisfied.
- Disabled actions explain exactly what is missing and how to resolve it.
- Grid connectivity is available at every PDN-bearing checkpoint.
- STA is stage-aware from Synthesis through Finish.
- Static and dynamic IR are available at physically meaningful stages with honest evidence classification.
- Power-grid EM is visible and cannot claim foundry pass without qualified limits.
- Signal EM remains an explicit `GAP` until a real implementation is validated.
- Product, Package, and Lab remain separate scopes.
- All important knobs are discoverable, typed, validated, and provenance-tracked.
- Geometry knobs operate only on candidates; analysis knobs never mutate geometry.
- `COMPLETED`, evidence validity, requirement pass, and signoff pass are never conflated.
- Aggregates cannot remain current when a dependency changes.
- No heavy job starts through navigation, tab selection, polling, or inspector opening.
- Native ASAP7 RTL-to-GDS end-to-end tests and all checkpoint analyses have reproducible evidence.
- UI, API, agent, native tools, logs, resource isolation, and documentation pass their acceptance gates.

## 13. Recommended first implementation slice

4. Normalize gridcheck and stage STA reports.
